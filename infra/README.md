# Merchantflo infrastructure (AWS Mumbai)

Terraform for the three environments — `dev`, `staging`, `production` — in `ap-south-1`
([decision 0003](../docs/decisions/0003-hosting-aws-mumbai.md)). Payment data, backups, logs and
Terraform state all stay in India.

```
infra/
  bootstrap/            once per AWS account: state bucket, ECR repository, GitHub OIDC roles
  stack/                one environment, composed from the modules below
  modules/network/      VPC over 3 AZs: public, app (NAT egress) and isolated database subnets; flow logs
  modules/data/         RDS PostgreSQL 16 (encrypted, PITR, force_ssl) and the app secrets
  modules/edge/         ALB (TLS 1.2+, HTTP→HTTPS, /readyz checks), WAF, access logs
  modules/service/      ECS Fargate: api/worker/migrate task definitions, services, autoscaling
  modules/monitoring/   SNS alarms, ops.metrics metric filters, CloudWatch dashboard
  envs/<environment>/   backend + sizing for each environment
```

## What runs where

```
internet ──443──▶ ALB + WAF ──3000──▶ api tasks (ROLE=api) ─┐
                                                           ├──5432──▶ RDS PostgreSQL (Multi-AZ in production)
                     worker tasks (ROLE=worker) ───────────┘
                     migrate task (ROLE=migrate), once per deploy
api/worker ──443 via NAT──▶ PSP APIs, merchant webhooks
```

| | dev | staging | production |
|---|---|---|---|
| NAT gateways | 1 | 1 | 1 per AZ |
| Database | db.t4g.micro, single-AZ, 7-day PITR | db.t4g.small, single-AZ, 7-day PITR | db.m7g.large, Multi-AZ, 35-day PITR, deletion protection |
| api tasks | 1–2 × 0.25 vCPU | 2–4 × 0.5 vCPU | 2–8 × 1 vCPU |
| worker tasks | 1 | 1 | 2 |
| Log retention | 14 days | 30 days | 365 days |
| Mock PSPs (test-mode merchants) | yes | yes | no |

Secrets (`DATABASE_URL`, `ADMIN_TOKEN`, `CUSTOMER_TOKEN_SECRET`, `CREDENTIALS_KEYS`) are generated
on the first apply, stored in Secrets Manager under `merchantflo-<env>/…` encrypted with the
environment's KMS key, and injected into containers at start. Terraform sets each value once;
rotation happens in Secrets Manager (see [deploy runbook](../docs/runbooks/deploy.md#rotating-secrets)).
Generated values are also in Terraform state, which is why the state bucket is KMS-encrypted,
versioned and readable only by founders.

## First-time setup (founder with AWS admin credentials)

1. **Bootstrap the account** (local state; keep `terraform.tfstate` from this step in the founders'
   password vault):
   ```sh
   terraform -chdir=infra/bootstrap init
   terraform -chdir=infra/bootstrap apply -var github_repository=<owner>/<repo>
   ```
   If the bucket name is taken, pass `-var state_bucket_name=…` and change `bucket` in each
   `envs/*/main.tf` backend block to match.
2. **GitHub settings** (repository → Settings):
   - Variables: `AWS_REGION=ap-south-1`, `ECR_REPOSITORY` and `AWS_BUILD_ROLE_ARN` from the bootstrap outputs.
   - Environments `dev`, `staging`, `production`, each with variables `AWS_DEPLOY_ROLE_ARN`
     (bootstrap output) and `PUBLIC_BASE_URL`; `production` with required reviewers.
   - `DEPLOY_ENABLED=true` once an environment exists (until then the deploy workflow skips).
3. **Push the first image**: merge to `main` with `DEPLOY_ENABLED` unset, then run the deploy
   workflow's build job — or build and push `merchantflo:<commit>` by hand.
4. **Certificate**: request an ACM certificate in `ap-south-1` for the API hostname
   (`api.staging.merchantflo.in` etc.) and validate it in DNS.
5. **Apply the environment**:
   ```sh
   terraform -chdir=infra/envs/staging init
   terraform -chdir=infra/envs/staging apply -var image_tag=<commit> -var certificate_arn=<arn> -var 'alarm_emails=["oncall@…"]'
   ```
   (or put those in `infra/envs/staging/terraform.tfvars`, which git ignores). Confirm the SNS
   subscription e-mail. Point the hostname at the `alb_dns_name` output.
6. **Migrate and start**: run the deploy workflow for the environment (it runs the migrate task,
   then rolls the services). The api refuses to start until migrations have run.
7. **Commit the provider lock files** generated by `init`, for every platform the team uses:
   `terraform -chdir=infra/envs/staging providers lock -platform=linux_amd64 -platform=darwin_arm64 -platform=windows_amd64`.

## Day to day

- **Deploys** don't touch Terraform: the pipeline registers new task definition revisions from the
  latest one with the new image ([deploy runbook](../docs/runbooks/deploy.md)).
- **Changing settings or sizing**: edit `envs/<env>/main.tf` (or `stack/` defaults), `plan`, `apply`.
  Environment variable and secret changes reach the tasks at the next deploy (redeploy the current
  image to apply them immediately).
- **Alarms**: [alerts runbook](../docs/runbooks/alerts.md). Drill them with `scripts/drills/alarm-drill.sh`.
- **Backups**: [backup and restore runbook](../docs/runbooks/backup-restore.md).

## Checks

CI runs `terraform fmt -check -recursive infra` and `terraform validate` on bootstrap and every
environment. `test/ops/infra.test.ts` checks the metric filters match the fields the worker logs.
